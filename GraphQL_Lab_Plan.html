◈ GraphQL Lab — Helpdesk API без REST

NestJS Lab дал вам полноценный REST-backend Helpdesk: CRUD тикетов, JWT-auth, живые обновления через WebSocket Gateway. Здесь тот же backend, тот же Prisma, тот же JWT — но HTTP-слой контроллеров из сессии 3 NestJS-лабы заменяется на GraphQL-резолверы. Домен не меняется специально: чтобы видеть именно то, что меняется при переходе на GraphQL, а не тонуть в новом коде.

Что нужно перед стартом: пройденная NestJS Lab — декораторы и reflect-metadata (раздел 1), provider scopes (раздел 2), Guards и JWT (раздел 5) используются здесь без повторного объяснения, только в новом контексте.

Домен: тот же Helpdesk — тикеты, комментарии, роли agent/customer, живые обновления. Меняется способ доступа к данным, а не сами данные.

Стек: @nestjs/graphql + Apollo Server, подход code-first (декораторы @ObjectType/@Field/@Resolver — прямое продолжение декораторного стиля из NestJS-лабы, а не отдельный DSL), dataloader для батчинга, тот же Prisma и Passport-JWT.

Термины отмечены надстрочной цифрой при первом появлении и ведут в глоссарий (раздел 10); там же — обратная ссылка ↩ к месту первого упоминания.

0. Зачем этот лаб и что дальше #

NestJS Lab (раздел 12, «Что дальше») сам называет этот шаг: тот же backend, но REST-эндпоинты сессии 3 заменяются на резолверы, а N+1 из раздела 4 возвращается на новом уровне. Это не новый проект — это тот же код, если сейчас на него посмотреть под другим углом.

1. Проблема: over/under-fetching в REST #

В REST-версии Helpdesk (NestJS-лаба, сессия 3) чтобы получить список тикетов с комментариями и именем исполнителя, фронтенду нужно либо получить от GET /tickets куда больше полей, чем реально нужно для списка (over-fetching — например, полный объект agent с его email и ролью, хотя на экране видно только имя), либо сделать отдельный запрос на каждый тикет за деталями (under-fetching — тот же N+1, только теперь на уровне HTTP-запросов, а не SQL).

РЕШЕНИЕ GRAPHQL Один endpoint (/graphql), и клиент сам описывает форму нужных данных в запросе — сервер отвечает ровно тем, что запрошено, ни байтом больше, за один round trip, независимо от глубины вложенности.

2. Типы, Query и Mutation (code-first) #

@ObjectType()
export class Ticket {
  @Field(() => Int)
  id: number;

  @Field()
  title: string;

  @Field()
  status: string;
}

@Resolver(() => Ticket)
export class TicketsResolver {
  constructor(private prisma: PrismaService) {}

  @Query(() => [Ticket])
  tickets() {
    return this.prisma.ticket.findMany();
  }
}
ПРЯМАЯ ПАРАЛЛЕЛЬ С NESTJS-ЛАБОЙ ObjectType1 и @Field() — те же декораторы, тот же механизм reflect-metadata из раздела 1 NestJS-лабы, просто вместо HTTP-маршрута они описывают узел GraphQL-схемы. Resolver2 при старте приложения читает эти метаданные со всех классов и генерирует файл схемы автоматически — вы не пишете .graphql-файл руками, он выводится из TypeScript-классов.
🔬 Под капотом: как autoSchemaFile превращает классы в SDL

При старте GraphQLModule.forRoot({ autoSchemaFile: true }) обходит все классы, помеченные @ObjectType(), @InputType() и @Resolver(), читает их метаданные (те же reflect-metadata-записи, что и в NestJS-лабе) и на основе этого строит объект схемы GraphQL в памяти, а затем сериализует его в файл schema.gql в формате SDL (Schema Definition Language) — человекочитаемого текстового описания типов. Файл создаётся заново при каждом старте приложения в режиме разработки, поэтому его обычно не коммитят в git, а добавляют в .gitignore.

3. Резолверы: parent, args, порядок вызова #

@ResolveField(() => [Comment])
comments(@Parent() ticket: Ticket) {
  return this.prisma.comment.findMany({ where: { ticketId: ticket.id } });
}
Зачем разбирать порядок вызова: GraphQL резолвит поля по одному узлу дерева запроса за раз — сначала выполнится резолвер tickets(), и только для каждого полученного тикета отдельно запустится comments(@Parent()3 ticket). Это не побочный эффект плохого кода — это буквально то, как работает граф резолверов в GraphQL, и именно это открывает дверь для N+1 в разделе 4.
🔬 Под капотом: резолвинг как обход дерева по уровням

GraphQL-исполнитель обходит запрошенное дерево полей breadth-first в пределах каждого уровня: сначала вычисляются все резолверы верхнего уровня (в вашем случае — один вызов tickets(), вернувший массив), затем для каждого элемента этого массива параллельно (через Promise.all внутри исполнителя) вызывается резолвер следующего уровня — comments. Именно слово "параллельно, но по одному вызову на элемент" и есть источник N+1: 10 тикетов — 10 отдельных, ничего не знающих друг о друге вызовов comments().

4. N+1 в резолверах и DataLoader #

N+14 из NestJS-лабы (раздел 4) лечился одним include в Prisma — потому что там вы сами писали один запрос. Здесь вы не контролируете, какие поля запросит клиент — GraphQL-запрос { tickets { comments { text } } } вызовет резолвер comments для каждого тикета по отдельности, а вы не знаете заранее, сколько их будет.

@Injectable({ scope: Scope.REQUEST })
export class CommentsLoader {
  public readonly batchComments = new DataLoader(async (ticketIds) => {
    const comments = await this.prisma.comment.findMany({
      where: { ticketId: { in: ticketIds as number[] } },
    });
    return ticketIds.map((id) => comments.filter((c) => c.ticketId === id));
  });
  constructor(private prisma: PrismaService) {}
}
ПОД КАПОТОМ DataLoader5 не выполняет запрос сразу — он копит все вызовы .load(id), поступившие в течение одного "тика" event loop (микрозадачи), и объединяет их в один batch-вызов колбэка с массивом всех накопленных id. Это тот же event loop, что вы разбирали в JS-лабе (сессия 5) — только здесь его особенность используется намеренно, как механизм батчинга.
🔬 Под капотом: на чём именно основан "один тик" DataLoader

Внутри библиотека dataloader использует process.nextTick (в Node.js) — это означает, что она откладывает выполнение batch-функции до момента, когда текущая синхронная часть кода полностью завершится, но раньше, чем управление вернётся к следующему циклу событий. На практике: все вызовы .load(), случившиеся синхронно один за другим внутри резолвинга одного GraphQL-запроса, гарантированно попадают в один batch — именно поэтому 10 параллельных вызовов резолвера comments из раздела 3 превращаются в один SQL-запрос, а не десять.

Зачем Scope.REQUEST: прямая связь с разделом 2 NestJS-лабы — DataLoader обязан быть новым на каждый HTTP-запрос: его внутренний кэш и очередь батча не должны переживать один запрос и тем более утекать в следующий, к другому пользователю.

5. Guards и контекст в GraphQL #

AuthGuard('jwt') и RolesGuard из NestJS-лабы (раздел 5) написаны в расчёте на HTTP ExecutionContext — context.switchToHttp().getRequest(). В GraphQL запрос устроен иначе (единый POST на /graphql), поэтому нужен один явный мостик — GqlExecutionContext6:

getRequest(context: ExecutionContext) {
  const ctx = GqlExecutionContext.create(context);
  return ctx.getContext().req;
}
ГЛАВНАЯ МЫСЛЬ Сам Guard, вся логика canActivate и RolesGuard — не меняются ни на строчку. Меняется только то, откуда Guard достаёт объект запроса. Это подтверждает, что Guard в разделе 5 NestJS-лабы был написан правильно с самого начала — абстракция ExecutionContext ровно для того и существует, чтобы не привязываться к транспорту.
🔬 Под капотом: почему обычный Middleware здесь бы не сработал

Middleware в Express/Nest привязан к HTTP-маршруту (пути и методу) — а у GraphQL всего один маршрут, POST /graphql, на который приходят вообще все запросы: и чтение списка тикетов, и мутация удаления. Middleware в принципе не может знать, какое GraphQL-поле сейчас резолвится — оно видит только "кто-то постучался в /graphql". Guard, в отличие от Middleware, получает доступ к GqlExecutionContext уже после того, как GraphQL-исполнитель определил, какой именно резолвер сейчас будет вызван — поэтому вся авторизационная логика в GraphQL-мире живёт в Guards, а не в Middleware, даже там, где в чистом REST можно было бы обойтись последним.

6. Subscriptions: живые данные без Gateway #

const pubSub = new PubSub();

@Subscription(() => Ticket)
ticketUpdated() {
  return pubSub.asyncIterableIterator('ticketUpdated');
}

@Mutation(() => Ticket)
async updateStatus(@Args('id') id: number, @Args('status') status: string) {
  const ticket = await this.prisma.ticket.update({ where: { id }, data: { status } });
  pubSub.publish('ticketUpdated', { ticketUpdated: ticket });
  return ticket;
}

🔬 Под капотом: почему стандартный PubSub не для продакшена

Класс PubSub из пакета graphql-subscriptions по умолчанию хранит подписчиков в памяти одного процесса — официальная документация Apollo прямо предупреждает, что эта реализация не подходит для продакшена. Проблема та же, что с комнатами Socket.IO из раздела 6 NestJS-лабы: если у вас несколько инстансов сервера за балансировщиком, мутация, обработанная одним инстансом, никак не уведомит подписчиков, подключённых к другому. Решение — PubSub-реализация поверх внешнего хранилища (обычно Redis), которое видно всем инстансам одинаково.

7. Тестирование резолверов #

it('возвращает тикеты', async () => {
  const module = await Test.createTestingModule({
    providers: [TicketsResolver, { provide: PrismaService, useValue: mockPrisma }],
  }).compile();
  const resolver = module.get(TicketsResolver);
  expect(await resolver.tickets()).toEqual([...]);
});
Зачем это выглядит так же, как в NestJS-лабе: резолвер — обычный provider с @Injectable под капотом декоратора @Resolver, поэтому Test.createTestingModule тестирует его абсолютно так же, как любой сервис в разделе 7 NestJS-лабы — GraphQL здесь не участвует вообще, только логика класса.
🔬 Под капотом: чего НЕ проверяет такой unit-тест

Схема GraphQL (SDL, раздел 2) собирается и валидируется только тогда, когда поднимается настоящий GraphQLModule — то есть в unit-тесте резолвера, как выше, вы не узнаете, если случайно поломали типы схемы (например, забыли @Field() на новом свойстве). Эту категорию ошибок ловит только e2e-тест шага 5.2, который реально отправляет строку GraphQL-запроса через /graphql и заставляет Apollo целиком провалидировать её против собранной схемы.

  • Отправьте на tickets() заведомо некорректный тип аргумента через Apollo Sandbox — где именно (Pipe, резолвер или Prisma) запрос будет отклонён, и почему на этом уровне?

9. Чек-лист концепций #

  • Over-fetching и under-fetching в REST — что именно решает единый GraphQL-endpoint.
  • Code-first: схема выводится из декорированных TypeScript-классов, а не пишется руками.
  • Резолвер поля вызывается по одному разу на каждый элемент родительского списка — источник N+1.
  • DataLoader: батчинг вызовов в пределах одного тика event loop + кэш на время запроса.
  • Почему DataLoader обязан быть Scope.REQUEST, а не singleton.
  • GqlExecutionContext — мостик между GraphQL-контекстом и обычным ExecutionContext Guard'ов.
  • Почему авторизационная логика в GraphQL живёт в Guards, а не в Middleware.
  • Subscription — типобезопасный канал событий поверх PubSub, отличие от WebSocket Gateway.
  • Резолвер тестируется как обычный provider — GraphQL не участвует в unit-тесте вообще, но и не проверяет схему.

10. Глоссарий терминов #

В порядке первого появления в тексте.

1. ObjectType ↩ — класс, декорированный @ObjectType(), описывающий узел GraphQL-схемы.

2. Resolver ↩ — класс, отвечающий за то, как получить данные для типа или конкретного поля.

3. Parent ↩ — результат резолвера родительского поля, доступный в резолвере вложенного поля через @Parent().

4. N+1 (GraphQL) ↩ — резолвер вложенного поля выполняется отдельно на каждый элемент родительского списка, порождая по одному запросу на элемент без батчинга.

5. DataLoader ↩ — утилита, объединяющая вызовы .load() в пределах одного тика event loop в один batch-запрос с кэшем на время его жизни.

6. GqlExecutionContext ↩ — обёртка, извлекающая объект запроса из GraphQL-контекста для повторного использования HTTP-ориентированных Guard'ов.

7. PubSub ↩ — внутренний брокер событий, на котором строятся Subscriptions; реализация по умолчанию хранит подписчиков в памяти одного процесса.

8. Apollo Sandbox ↩ — встроенный веб-интерфейс для ручного выполнения GraphQL-запросов при разработке.

9. Subscription ↩ — третий вид GraphQL-операции (наряду с Query и Mutation), открывающий канал событий для клиента.
