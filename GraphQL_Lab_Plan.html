1. Прежде чем начать: типичные заблуждения о GraphQL и как их учитывает план #

GraphQL легко «попробовать» за вечер: пара декораторов — и запросы работают. Проблемы начинаются позже: сотни SQL на один запрос, падающая целиком страница из-за одного поля, подписки, которые перестают приходить после масштабирования. Ниже — нюансы, которые план специально выносит на поверхность, чтобы вы наткнулись на них осознанно, а не на проде.

💡 GraphQL — это не база данных и не «SQL для фронтенда»

Название вводит в заблуждение: «Query Language» тут — язык запросов к API, а не к данным. GraphQL ничего не знает о таблицах, индексах и JOIN. Сервер описывает схему1 — набор типов и полей, — а для каждого поля пишет функцию-резолвер2, которая достаёт значение откуда угодно: из PostgreSQL, Redis, другого HTTP-сервиса, из памяти. Клиент видит только схему. Один и тот же тип Movie может собираться из трёх разных источников — клиенту это безразлично.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

В лабе резолверы — тонкий слой: разбирают аргументы и делегируют в сервисы и загрузчики, которые ходят в PostgreSQL через Prisma. Вы увидите, что форма схемы (Movie.director, Movie.averageRating) намеренно не совпадает с формой таблиц (movies.director_id, агрегат по reviews).

💡 «Клиент запросит ровно то, что нужно» — значит, и то, что вы не ожидали

Гибкость — главное преимущество GraphQL и главный источник проблем. REST-эндпоинт делает ровно то, что вы в нём написали. GraphQL-запрос собирает клиент: он может запросить 50 фильмов, у каждого — актёров, у каждого актёра — фильмографию, у каждого фильма в ней — рецензии… Наивная реализация резолверов на такой запрос делает N+13 запросов к базе (а на вложенных уровнях — N×M), и сервер ложится от одного «любопытного» клиента.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

N+1 вы сначала воспроизведёте и посчитаете (шаг 3.2), потом уберёте через DataLoader4 (шаг 4.1), а в сессии 3 поставите ограничения глубины и сложности запросов (шаг 6.4). Эти три вещи — обязательный минимум любого продового GraphQL, а не «оптимизация на потом».

💡 Один эндпоинт, HTTP 200 — и всё равно ошибка

В GraphQL обычно один URL (POST /graphql), и сервер часто отвечает 200 OK, даже если часть запроса упала: ошибки лежат в поле errors тела ответа, рядом с частично заполненным data. Мониторинг «по статус-кодам», HTTP-кэш по URL, логи nginx — всё это перестаёт работать так, как вы привыкли в REST.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Разделы 7 и шаг 5.1: единый формат ошибок с машинно-читаемым extensions.code5, маскировка внутренних ошибок в production, осознанное проектирование nullability, чтобы одно упавшее поле не обнуляло всю страницу.

💡 Code-first и schema-first — это не про «удобнее», а про источник истины

Есть два подхода. Schema-first: пишете SDL6 руками (type Movie { ... }), по нему генерируются типы TypeScript. Code-first7: пишете классы с декораторами, схема генерируется из кода. Оба рабочие. Ловушка code-first — забыть, что схема всё равно есть и это публичный контракт: переименовали свойство класса — сломали всех клиентов, даже не заметив.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Выбран code-first (@nestjs/graphql), но сгенерированный src/schema.gql коммитится в git. Каждое изменение схемы видно в diff'е как изменение контракта, а в Production Hell вы прогоните автоматическую проверку breaking changes.

💡 Подписки «работают» — пока у вас один процесс

Подписка8 — долгоживущее WebSocket-соединение, по которому сервер пушит события. Стандартный PubSub из graphql-subscriptions хранит подписчиков в памяти процесса. Запустите второй инстанс — и мутация, пришедшая на инстанс A, никогда не долетит до клиента, подписанного на инстанс B. Документация об этом предупреждает одной строкой, которую все пропускают.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Шаг 6.1 — подписки на in-memory PubSub; шаг 6.2 — вы запускаете два инстанса, видите, как события теряются, и переключаете PubSub на Redis одной переменной окружения.

💡 В GraphQL нет /v2 — и это не баг

REST-API часто версионируют URL'ом. GraphQL-схему принято развивать аддитивно: новые поля и типы добавляются, старые помечаются @deprecated9 и удаляются, когда их перестали запрашивать. Это работает, только если вы знаете, какие поля кто использует, и умеете ловить breaking changes до деплоя.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Задание Production Hell №5: удалить поле «по-плохому», поймать поломку, затем сделать то же через @deprecated и сравнение схем.

Каталог фильмов — хрестоматийно «графовые» данные: фильм → режиссёр → его фильмы → их актёры → их фильмография. 2. Как GraphQL устроен внутри: язык, типы, выполнение #

2.1. Язык запросов: операция, selection set, аргументы

Документ GraphQL состоит из операций10 (query, mutation, subscription) и фрагментов. Операция — это дерево полей: в фигурных скобках — selection set11, набор полей, которые вы хотите получить у объекта. Ответ повторяет форму запроса один в один.

query MoviePage($id: ID!, $withCast: Boolean = true) {   # имя операции + переменные
  movie(id: $id) {                  # поле с аргументом
    title
    year
    director { name }               # вложенный selection set
    cast @include(if: $withCast) {  # директива
      character
      person { ...PersonCard }      # фрагмент
    }
    latest: reviews(first: 3) {     # алиас: поле называется latest в ответе
      edges { node { rating text } }
    }
  }
}

fragment PersonCard on Person { id name bornYear }
  • Переменные12 ($id) передаются отдельно от текста запроса в JSON. Текст запроса остаётся неизменным, поэтому его можно кэшировать и валидировать один раз. Никогда не склеивайте значения в строку запроса — это аналог SQL-инъекции.
  • Алиас13 переименовывает поле в ответе и позволяет запросить одно поле дважды с разными аргументами (top: reviews(first:1), all: reviews(first:50)).
  • Фрагмент14 — переиспользуемый кусок selection set, привязанный к типу (on Person). Инлайн-фрагмент ... on Movie { title } нужен для полиморфных полей (раздел 2.2).
  • Директивы15 @include(if:) / @skip(if:) включают и выключают поля в зависимости от переменной.

2.3. Три корневых типа: Query, Mutation, Subscription

Схема имеет до трёх корневых типов21 — точек входа. Их поля — это и есть «эндпоинты» вашего API.

  • Query — чтение. Поля верхнего уровня выполняются параллельно (спецификация разрешает любой порядок), поэтому у них не должно быть побочных эффектов.
  • Mutation22 — изменение. Поля верхнего уровня выполняются строго последовательно: в mutation { a: addReview(...) b: deleteReview(...) } второе начнётся только после завершения первого. Всё, что ниже верхнего уровня (выбранные поля результата), снова выполняется как обычный query.
  • Subscription — поток событий. Одна операция — одно поле верхнего уровня; сервер выполняет selection set заново на каждое событие.

Технически разница между query и mutation — только в порядке выполнения и в договорённости. Сервер не запретит вам менять данные в резолвере query — но кэши клиентов, retry-логика и GET-запросы будут считать его безопасным.

2.4. Жизненный цикл запроса: parse → validate → execute

POST /graphql  { "query": "...", "variables": {...}, "operationName": "MoviePage" }
   │
   ▼  1. PARSE      текст → AST (дерево узлов: OperationDefinition, Field, Argument...)
   │                синтаксическая ошибка → errors, data отсутствует, выполнение не начинается
   ▼  2. VALIDATE   AST сверяется со схемой: поля существуют? типы аргументов верны?
   │                фрагменты применимы? переменные объявлены? + ваши правила (глубина!)
   │                ошибка валидации → errors, data отсутствует
   ▼  3. EXECUTE    обход дерева полей, вызов резолверов, сбор результата,
   │                проверка nullability, ошибки полей → errors + частичный data
   ▼
{ "data": {...}, "errors": [...]?, "extensions": {...}? }

AST23 (abstract syntax tree) — это ваш запрос, разобранный в объекты. Валидация работает только с AST и схемой, без выполнения — поэтому именно на этапе validate можно дёшево отбросить слишком глубокие запросы (вы напишете своё правило валидации в шаге 6.4). Apollo кэширует результаты parse+validate по тексту запроса, так что одинаковые запросы не парсятся заново.

2.5. Резолверы: четыре аргумента и резолвер по умолчанию

Каждое поле каждого типа имеет резолвер — функцию с сигнатурой (parent, args, context, info):

АргументЧто внутриВ NestJS
parent (root, source)значение, которое вернул резолвер родительского поля@Parent()
argsаргументы этого поля (уже проверенные по типам)@Args('id')
context24один объект на весь запрос: пользователь, загрузчики, req@Context()

Для 90% полей резолвер писать не нужно: резолвер по умолчанию25 просто берёт parent[fieldName]. Резолвер Query.movie вернул объект из Prisma { id: 1, title: 'Inception', directorId: 7 } — поля title и year отдадутся «сами». А вот поля director в объекте нет — для него нужен явный резолвер, который по parent.directorId найдёт человека. В NestJS такие резолверы называются @ResolveField26.

2.6. Как выполняется дерево и откуда берётся N+1

Исполнитель обходит дерево уровень за уровнем. Для списка он вызывает резолверы дочерних полей для каждого элемента по отдельности — резолвер ничего не знает о соседях:

movies(limit: 10)                         → 1 SQL:  SELECT * FROM movies LIMIT 10
 ├─ [0].director  → resolve(parent=m0)    → 1 SQL:  SELECT * FROM persons WHERE id = 7
 ├─ [1].director  → resolve(parent=m1)    → 1 SQL:  SELECT * FROM persons WHERE id = 7   (тот же!)
 ├─ ...
 └─ [9].director  → resolve(parent=m9)    → 1 SQL
                                             итого: 1 + 10 = 11 запросов («N+1»)

Добавьте cast { person { name } } — и получите ещё 10 запросов за составом плюс по запросу на каждого актёра. Хитрость в том, что все эти резолверы вызываются синхронно в одном тике event loop'а и возвращают промисы. Если собрать все запрошенные id за этот тик и сделать один WHERE id IN (...) — получится батчинг. Именно это и делает DataLoader (раздел 5).

2.7. Ошибки и «всплытие null»

Если резолвер бросил исключение, GraphQL не роняет весь запрос: значение поля становится null, а в errors добавляется запись с path — путём до поля. Но если поле объявлено как non-null (!), null там недопустим — и null всплывает27 к ближайшему nullable-родителю. Подробный разбор — в разделе 7.

2.8. Интроспекция и __typename

Схема GraphQL описывает сама себя: специальные поля __schema и __type — интроспекция28 — возвращают все типы, поля, аргументы и описания. Так работают автодополнение в GraphiQL, генераторы типов для клиентов и документация. В production интроспекцию часто выключают (меньше подсказок атакующему), хотя это не защита, а лишь неудобство для него. Поле __typename29 есть у любого объектного типа и возвращает имя конкретного типа — без него невозможно различить элементы юниона, а клиентские кэши (Apollo Client, urql) строят ключи как __typename + id.

2.9. Транспорт: GraphQL поверх HTTP и WebSocket

Спецификация GraphQL не определяет транспорт. Фактический стандарт — GraphQL over HTTP: POST с JSON-телом {query, variables, operationName} (или GET с параметрами в URL — только для query). Ответ — JSON с data/errors. Для подписок используется WebSocket с протоколом graphql-ws30 (подпротокол graphql-transport-ws): клиент шлёт connection_init, сервер отвечает connection_ack, дальше subscribe → поток next → complete. Старый протокол subscriptions-transport-ws заброшен и в свежих версиях NestJS удалён — если увидите его в туториале, туториал устарел.

Browser ──POST /graphql──► Express ─► Apollo Server
                                        │ parse → validate (+depthLimit) → complexity plugin
                                        │ context(): { user из JWT, loaders: new DataLoader'ы }
                                        ▼
                               Query.movie  (MoviesResolver)  ──► MoviesService ──► Prisma ──► PostgreSQL

🔬 Под капотом: почему у типа Movie два резолвера из разных модулей

5. Проблема N+1 и DataLoader #

Если из всей лабы запомнить одну вещь, то эту: в GraphQL каждый резолвер поля вызывается отдельно для каждого родителя, и без батчинга количество SQL-запросов растёт вместе с размером ответа. Это не баг NestJS или Prisma — это следствие модели выполнения (раздел 2.6).

Проблема без DataLoader

query {
  movies(limit: 10) {
    title
    director { name }
    cast { character person { name } }
  }
}
Резолвер                     Вызовов   SQL на вызов   Итого
Query.movies                  1         1              1
Movie.director               10         1             10    ← один и тот же Нолан загружен 3 раза
Movie.cast                   10         1             10
CastCredit.person            21         1             21    ← Майкл Кейн загружен 3 раза
                                                     ────
                                                     ≈43 SQL на один запрос

На локалке с 10 фильмами это незаметно — ≈43 запроса по 1 мс. На проде с limit: 50, сетевой задержкой до БД 2 мс и пулом в 10 соединений — это уже сотни миллисекунд и забитый пул. А клиент может вложить ещё уровень, и получится N×M.

Решение с DataLoader

DataLoader — маленькая библиотека (≈400 строк) с одной идеей: отложить загрузку до конца текущего тика и собрать все ключи в один батч.

Тик 1 (синхронно):  Movie.director(m0) → loader.load(7)   ─┐  ключи копятся,
                    Movie.director(m1) → loader.load(7)    │  промисы возвращаются
                    Movie.director(m2) → loader.load(12)   │  сразу, но не разрешены
                    ...                                    ─┘
Конец тика:         batchFn([7, 12, 3, ...])   ← дубликаты уже убраны кэшем
                    → SELECT * FROM persons WHERE id IN (7, 12, 3, ...)   (1 запрос!)
                    → результаты раздаются промисам в том же порядке, что ключи

С загрузчиками тот же запрос выполняется за 4 SQL, независимо от limit: фильмы, режиссёры одним IN, составы одним IN, актёры одним IN.

Три правила, без которых DataLoader сломает вам данные:

  1. Контракт batch-функции. Она получает массив ключей и обязана вернуть массив той же длины в том же порядке. База вернёт строки в произвольном порядке и без отсутствующих id — поэтому результат всегда пересобирается через Map, а для отсутствующих ключей ставится null или Error.
  2. Один набор загрузчиков — на один запрос. У DataLoader есть кэш (memoization) по ключу. Если загрузчик будет синглтоном, кэш переживёт запрос: пользователь увидит устаревшие данные, а в худшем случае — данные, загруженные в контексте чужих прав. Загрузчики создаются в context() на каждый HTTP-запрос / каждую операцию подписки (шаг 4.1; задание Production Hell №2 — нарушить это правило и посмотреть).
  3. Группирующие загрузчики для «один-ко-многим». Для Movie.cast ключ — movieId, а значение — массив ролей. Batch-функция делает WHERE movie_id IN (...) и раскладывает строки по группам; для фильма без актёров — пустой массив, а не отсутствие элемента.
🔬 Под капотом: что такое «конец тика» и почему батч не соберётся через await

DataLoader по умолчанию планирует batch-функцию через process.nextTick (с поправкой на очередь промисов). Исполнитель GraphQL обходит поля одного уровня синхронно: для каждого из 10 фильмов вызывает резолвер director, каждый вызывает loader.load() и возвращает промис. Все 10 вызовов происходят до того, как event loop получит управление, — поэтому ключи успевают накопиться.

Отсюда ловушка: если внутри резолвера сделать await somethingElse() до load(), вызовы размажутся по разным тикам и батч развалится на несколько. Пример: резолвер сначала проверяет права через отдельный запрос, потом вызывает загрузчик. Правило: load() — как можно раньше, дополнительные асинхронные шаги — через тот же механизм загрузчиков.

🔬 Под капотом: почему не REQUEST-scoped провайдеры NestJS

В NestJS можно объявить провайдер с scope: Scope.REQUEST — Nest будет создавать его заново на каждый запрос. Кажется, идеально для загрузчиков. Но request scope «заражает» всю цепочку зависимостей: каждый, кто его инжектит, тоже становится request-scoped и пересоздаётся на каждый запрос, включая резолверы. Для GraphQL, где на один запрос может вызываться много резолверов, это заметный оверхед и источник странных багов (в подписках HTTP-запроса нет вообще).

Поэтому в лабе LoadersFactory — обычный синглтон, а экземпляры загрузчиков создаются в функции context() GraphQL-модуля и живут в контексте запроса. Резолверы получают их через @Context('loaders'). Это стандартный паттерн, рекомендуемый и в документации DataLoader.

7. Ошибки, nullability и частичные ответы — как это реально работает #

Формат ошибки

{
  "data": { "movie": { "title": "Inception", "reviews": { "edges": [
    { "node": { "rating": 9, "author": { "name": "Борис", "email": null } } }
  ] } } },
  "errors": [
    {
      "message": "Email виден только владельцу",
      "locations": [{ "line": 5, "column": 35 }],
      "path": ["movie", "reviews", "edges", 0, "node", "author", "email"],
      "extensions": { "code": "FORBIDDEN" }
    }
  ]
}
  • message — для людей; клиентский код не должен парсить текст.
  • path — путь до поля в ответе (с индексами массивов). По нему клиент понимает, какой именно null — «нет данных», а какой — «ошибка».
  • locations — место в тексте запроса.
  • extensions — произвольный объект; по соглашению extensions.code — машинный код: UNAUTHENTICATED, FORBIDDEN, BAD_USER_INPUT, NOT_FOUND, INTERNAL_SERVER_ERROR и ваши доменные (ALREADY_REVIEWED).

Всплытие null

Правило: если резолвер поля упал (или вернул null), поле становится null. Если поле non-null — null недопустим, и «ноль» передаётся родителю; если и родитель non-null — дальше вверх, пока не встретится nullable-поле. Если nullable-полей на пути нет, data целиком становится null.

Схема: movies: [Movie!]!   Movie.director: Person!   Person.name: String!
Упал резолвер director у фильма #3:

  director (Person!)  → null недопустим ─┐
  Movie #3 (Movie!)   → null недопустим ─┤  элемент списка non-null
  movies ([Movie!]!)  → null недопустим ─┤  сам список non-null
  data                → null  ◄──────────┘  ВЕСЬ ответ пуст из-за одного режиссёра

С Movie.director: Person (nullable):
  director → null, остальные 9 фильмов и поля фильма #3 на месте, в errors — одна запись
Где ставить !Где оставлять nullable
Скаляры, которые физически всегда есть: id, title, ratingПоля, резолвер которых может упасть независимо от родителя: другой сервис, права доступа (email)
Списки: [T!]! — пустой список лучше, чем nullВычисляемые поля без значения: averageRating у фильма без рецензий
Связи, гарантированные внешним ключом в той же БД (Review.movie)Корневые «найди по id»: movie(id) — «не найдено» = null, а не ошибка

Nullable → non-null — breaking change для клиентов? Нет, наоборот: сделать поле non-null безопасно (клиент уже готов к null), а вот non-null → nullable ломает клиентов, которые на null не рассчитывали. Поэтому при сомнении начинайте с nullable.

Ошибки в errors или ошибки как данные

Есть два стиля. Ошибки в errors (используется в лабе) — просто и стандартно, но ошибки не типизированы в схеме: клиент не знает из интроспекции, какие коды бывают. Ошибки как данные31: мутация возвращает юнион union AddReviewResult = Review | AlreadyReviewed | ValidationFailed, и клиент обязан обработать каждый вариант через __typename. Прагматичное правило: ожидаемые бизнес-исходы (уже оставил рецензию, фильм снят с публикации) — данными; исключения (нет прав, упала БД, невалидный ввод) — в errors.

🔬 Под капотом: какой HTTP-статус вернуть

Исторически GraphQL-серверы отвечали 200 почти всегда. Современная спецификация GraphQL over HTTP вводит медиатип application/graphql-response+json: при нём ошибки парсинга и валидации (когда выполнение даже не началось) отдаются с 4xx, а ответ с частичными данными — 200. Apollo Server так и делает: синтаксическая ошибка → 400, ошибка валидации → 400, упавшее поле → 200 с errors.

Практический вывод для мониторинга: доля HTTP 5xx у GraphQL почти ничего не говорит. Метрики строят по errors[].extensions.code и по operationName — поэтому клиентам нужно всегда именовать операции (query MoviePage, а не анонимный query).

Кэширование

  • HTTP-кэш / CDN плохо работает с POST /graphql: у всех запросов один URL. Решения — GET-запросы для query + persisted queries (короткий URL с хешем) и заголовки Cache-Control.
  • Клиентский нормализованный кэш (Apollo Client, urql): ответы раскладываются по ключам __typename:id. Обновили рецензию мутацией, вернули { id rating } — все экраны, где она показана, обновились. Поэтому мутации должны возвращать изменённый объект, а не Boolean (исключение — удаление).
  • Серверный кэш резолверов (Redis) — как в REST, но на уровне полей/загрузчиков. DataLoader — это кэш в рамках одного запроса, не путайте.
🔬 Под капотом: почему пагинация внутри списка всё равно N+1

Movie.reviews(first: 5) на одном фильме — один запрос. Но movies(limit: 20) { reviews(first: 5) { ... } } — это 20 запросов «первые 5 рецензий фильма X»: обычный WHERE movie_id IN (...) не умеет «по 5 на каждый». В SQL это решается оконной функцией (ROW_NUMBER() OVER (PARTITION BY movie_id ORDER BY id DESC)) или LATERAL JOIN — через $queryRaw в Prisma. Это задание Production Hell №1. Второй вариант — ограничить сложностью: вложенная пагинация дорогая, и complexity-анализ должен это отражать.

🔬 Под капотом: зачем четыре пакета ради одного GraphQL

🔬 Под капотом: что изменилось в Prisma 7 и зачем правка tsconfig.build.json

В Prisma 7 клиент больше не «живёт» в node_modules/.prisma: генератор prisma-client кладёт исходники клиента прямо в проект (output), и их компилирует ваш TypeScript. Движок на Rust убран — запросы идут через driver adapter (@prisma/adapter-pg поверх обычного драйвера pg). А URL базы для CLI (миграции, seed) переехал в prisma.config.ts; .env Prisma сама больше не читает — отсюда import 'dotenv/config'.

Правка tsconfig.build.json — неочевидная ловушка. Если nest build увидит prisma.config.ts и prisma/seed.ts в корне api/, TypeScript посчитает корнем исходников api/, а не api/src/, и положит сборку в dist/src/main.js вместо dist/main.js. npm run start:prod после этого падает с «Cannot find module dist/main». Клиент сгенерирован в src/generated — внутри src, поэтому структура сборки не ломается.

Почему у CastMember составной ключ из трёх полей: один актёр может сыграть в фильме двух персонажей — тогда пара (movieId, personId) не уникальна.

🔬 Под капотом: что происходит при старте code-first приложения

При инициализации GraphQLModule сканирует все провайдеры приложения в поисках классов с @Resolver(), собирает метаданные декораторов (@ObjectType, @Field, @Query…), строит из них объект GraphQLSchema средствами graphql-js, печатает его в SDL и пишет в autoSchemaFile. 🔬 Под капотом: когда тип в @Field обязателен

Декораторы получают тип свойства через reflect-metadata (флаг emitDecoratorMetadata в tsconfig): для title: string TypeScript записывает в метаданные String, и @Field() без аргументов понимает, что это String!. Но метаданные беднее системы типов TS:

  • number превращается в Number, а GraphQL не знает, Int это или Float — по умолчанию выберет Float. Поэтому @Field(() => Int) явно.
  • string | null — объединение; в метаданных окажется Object, и сборка схемы упадёт с «Undefined type error». Отсюда @Field(() => String, { nullable: true }).
  • Массивы теряют тип элемента (Array) — нужен () => [Genre].
  • ID в GraphQL сериализуется строкой: наш id: 1 клиент получит как "1", а в аргументы он придёт тоже строкой.

Функция () => Type (а не просто Type) нужна из-за циклических импортов: Movie ссылается на Person, Person — на Movie; ленивая функция вызывается уже после загрузки всех модулей. Существует CLI-плагин @nestjs/graphql, который расставляет @Field автоматически по типам TS, но в лабе мы пишем всё явно — чтобы видеть, что именно попадает в контракт.

🔬 Под капотом: CSRF prevention и «простые» запросы

Браузер может отправить на чужой домен «простой» запрос без preflight-проверки CORS: GET или POST с Content-Type из списка text/plain, application/x-www-form-urlencoded, multipart/form-data. Apollo Server по умолчанию отклоняет запросы, которые могли быть простыми: без Content-Type: application/json и без заголовков apollo-require-preflight / x-apollo-operation-name. Любой «непростой» заголовок заставляет браузер сделать preflight, и CORS-политика сервера решит, пускать ли.

В ответе интроспекции тип title: String! выглядит как { kind: NON_NULL, ofType: { kind: SCALAR, name: String } }, а genres: [Genre!]! — как NON_NULL → LIST → NON_NULL → ENUM. Именно эти вложенные обёртки разворачивают генераторы типов для клиентов.

/** Загрузчик «один объект по id». Контракт: результат той же длины и в том же порядке, что ids. */
function byId<T extends { id: number }>(label: string, fetch: (ids: number[]) => Promise<T[]>) {
  return new DataLoader<number, T>(async (ids) => {
    const rows = await fetch([...ids]);
    const map = new Map(rows.map((r) => [r.id, r]));
    return ids.map((id) => map.get(id) ?? new Error(`${label} ${id} not found`));
  });
}

/** Загрузчик «много объектов по внешнему ключу» (один-ко-многим). Для ключа без строк — []. */
function groupedBy<T>(key: keyof T, fetch: (ids: number[]) => Promise<T[]>) {
  return new DataLoader<number, T[]>(async (ids) => {
    const rows = await fetch([...ids]);
    const groups = new Map<number, T[]>();
    for (const row of rows) {
      const k = row[key] as unknown as number;
      const list = groups.get(k);
      if (list) list.push(row);
      else groups.set(k, [row]);
    }
    return ids.map((id) => groups.get(id) ?? []);
  });
}

🔬 Под капотом: почему Error, а не throw, и что делает кэш

Batch-функция может «уронить» отдельный ключ, вернув для него экземпляр Error вместо значения: промис именно этого load() будет отклонён, а остальные — разрешены. Если же бросить исключение из самой batch-функции, упадут все ключи батча — одна битая запись сломает 10 режиссёров.

Кэш DataLoader — это Map<key, Promise>. Второй load(7) в том же запросе не добавит ключ в батч, а вернёт тот же промис. Поэтому в логе IN (...) содержит каждого человека один раз, хотя Майкл Кейн встречается в трёх фильмах. Внимание: кэшируется и ошибка — повторный load того же ключа сразу вернёт отклонённый промис.

Порядок в IN (...) — порядок первых вызовов load(), а порядок строк из PostgreSQL произвольный. Именно поэтому Map обязателен: вернуть rows как есть — классический баг, при котором у фильма оказывается чужой режиссёр, причём не всегда, а «иногда».

@Injectable()
export class AuthService {
  constructor(private readonly prisma: PrismaService, private readonly jwt: JwtService) {}

  async register(input: RegisterInput) {
    const email = input.email.toLowerCase();
    if (await this.prisma.user.findUnique({ where: { email } })) {
      throw gqlError('EMAIL_TAKEN', 'Пользователь с таким email уже есть');
    }
    const user = await this.prisma.user.create({
      data: { email, name: input.name, passwordHash: await bcrypt.hash(input.password, 10) },
    });
    return this.issue(user);
  }

  async login(input: LoginInput) {
    const user = await this.prisma.user.findUnique({ where: { email: input.email.toLowerCase() } });
    // одинаковое сообщение для «нет такого» и «неверный пароль» — не подсказываем, какие email существуют
    if (!user || !(await bcrypt.compare(input.password, user.passwordHash))) {
      throw gqlError('UNAUTHENTICATED', 'Неверный email или пароль');
    }
    return this.issue(user);
  }

  private issue(user: { id: number; role: Role }) {
    return { token: this.jwt.sign({ sub: user.id, role: user.role }), user };
  }

  /** Вызывается из context() на каждый запрос. Никогда не бросает: нет/битый токен → аноним. */
  async userFromHeader(header?: string | null): Promise<AuthUser | null> {
    if (!header?.startsWith('Bearer ')) return null;
    try {
      const payload = await this.jwt.verifyAsync<{ sub: number; role: Role }>(header.slice(7));
      return { id: payload.sub, role: payload.role };
    } catch {
      return null;
    }
  }
}

🔬 Под капотом: почему guard в GraphQL — это не guard в REST

В REST guard стоит «на входе» эндпоинта и отвечает 401 на весь запрос. В GraphQL guard висит на резолвере: @UseGuards(GqlAuthGuard) на мутации addReview отработает, только если клиент запросил именно это поле. Отказ guard'а — это ошибка поля: она попадает в errors с path, а остальные поля запроса выполняются как обычно.

ExecutionContext в Nest универсален: для HTTP он хранит req/res, для GraphQL — четвёрку (root, args, context, info). GqlExecutionContext.create() переупаковывает его, и getContext() возвращает тот самый объект, который вернула наша функция context(). Стандартный AuthGuard('jwt') из Passport ожидает req — поэтому в GraphQL его приходится переопределять через getRequest(). Мы пошли проще: пользователь уже разобран в контексте, guard только проверяет наличие. Бонус: этот же guard без изменений будет работать для подписок, где никакого req нет.

Почему userFromHeader глотает ошибку битого токена: иначе один протухший токен ломал бы даже публичные запросы (каталог не загрузится, потому что токен истёк). Цена — клиент не узнает, что токен истёк, пока не обратится к закрытому полю и не получит UNAUTHENTICATED. Это типичный компромисс; альтернатива — отдельный код TOKEN_EXPIRED.

🔬 Под капотом: undefined против null в мутациях обновления

В GraphQL у необязательного аргумента три состояния: не передан, передан null, передан значение. Для «патча» это важно: updateReview(input: {id: 5, rating: 8}) не должен стирать текст, а {id: 5, text: null} — должен. Apollo передаёт в резолвер объект без ключа для непереданных полей, class-transformer сохраняет это как undefined, а Prisma трактует undefined как «не трогать поле», а null — как «записать NULL». Поэтому data: { rating: input.rating, text: input.text } работает корректно без единого if.

Мутация возвращает полный объект Review, а не Boolean: клиент в том же запросе выбирает нужные поля (включая movie { averageRating } — уже пересчитанный), а клиентский кэш обновляет рецензию по __typename + id без повторного запроса. deleteReview возвращает Boolean — объекта уже нет; альтернатива — вернуть ID удалённой записи.

Почему P2002 ловим по коду, а не через instanceof Prisma.PrismaClientKnownRequestError: в Prisma 7 класс ошибок живёт в сгенерированном клиенте, и проверка «по форме» устойчивее к путям импорта. Коды ошибок Prisma стабильны и описаны в документации.

// src/graphql/format-error.ts
import { Logger } from '@nestjs/common';
import { unwrapResolverError } from '@apollo/server/errors';
import type { GraphQLFormattedError } from 'graphql';

const logger = new Logger('GraphQL');

export function formatGqlError(formatted: GraphQLFormattedError, error: unknown): GraphQLFormattedError {
  const ext = (formatted.extensions ?? {}) as Record<string, unknown>;
  const code = ext.code as string | undefined;

  // 1. ValidationPipe бросает BadRequestException → Nest кладёт массив сообщений в originalError.
  //    Приводим к единому коду BAD_USER_INPUT с машинно-читаемыми деталями.
  const original = ext.originalError as { message?: unknown } | undefined;
  if (code === 'BAD_REQUEST' && Array.isArray(original?.message)) {
    return {
      message: 'Некорректные входные данные',
      locations: formatted.locations,
      path: formatted.path,
      extensions: { code: 'BAD_USER_INPUT', details: original.message },
    };
  }

  // 2. Неожиданная ошибка (throw new Error, упавшая БД...): полный стек — в лог,
  //    клиенту в production — только нейтральное сообщение.
  if (!code || code === 'INTERNAL_SERVER_ERROR') {
    const raw = unwrapResolverError(error);
    logger.error(`${formatted.message} at ${formatted.path?.join('.')}`, raw instanceof Error ? raw.stack : undefined);
    if (process.env.NODE_ENV === 'production') {
      return { message: 'Internal server error', path: formatted.path, extensions: { code: 'INTERNAL_SERVER_ERROR' } };
    }
  }

  // 3. Ожидаемые ошибки (gqlError) — как есть, но без stacktrace и внутренностей
  const { stacktrace: _stack, originalError: _orig, ...safe } = ext;
  return { ...formatted, extensions: safe };
}

🔬 Под капотом: GraphQLError, originalError и откуда Apollo берёт код

Всё, что бросил резолвер, исполнитель graphql-js оборачивает в GraphQLError, добавляя path и locations; исходное исключение сохраняется в originalError. Если вы сами бросили GraphQLError с extensions.code (наш gqlError), код сохранится. Если бросили обычный Error — Apollo поставит INTERNAL_SERVER_ERROR. Исключения Nest (BadRequestException, ForbiddenException…) драйвер @nestjs/apollo переводит в коды по HTTP-статусу и кладёт тело исключения в extensions.originalError.

formatError вызывается для каждой ошибки непосредственно перед отправкой ответа — это последний рубеж. Даже если в коде кто-то бросит ошибку с текстом SQL или куском данных другого пользователя, в production клиент увидит только «Internal server error». unwrapResolverError достаёт исходное исключение из обёртки — именно его стек нужен в логе.

Обратите внимание на эксперимент D: два алиаса одного поля — это два независимых резолвера, и ошибка одного не трогает другой. Поэтому клиенты, склеивающие несколько «виджетов» в один запрос, выигрывают от nullable-корней.

🔬 Под капотом: resolveType и почему без него исполнитель беспомощен

Когда поле имеет абстрактный тип (интерфейс или юнион), исполнитель получает от резолвера просто объект и должен решить, какой он конкретный тип: от этого зависит, какие инлайн-фрагменты применять и что вернуть в __typename. Для этого у абстрактного типа есть функция resolveType. Объекты из Prisma не несут имени типа, поэтому мы добавили дискриминатор kind для кредитов и проверку «есть ли title» для поиска. Ошибка в resolveType — одна из самых неприятных: запрос проходит, но фрагменты молча не срабатывают.

Валидация фрагментов идёт по схеме: ... on CastCredit { character } внутри filmography допустим, потому что CastCredit реализует Credit. А ... on Review там же — ошибка валидации: «Fragment cannot be spread here as objects of type Credit can never be of type Review».

Заметьте: в search мы не используем загрузчики — это корневое поле, оно вызывается один раз на запрос, N+1 здесь не бывает. Загрузчики нужны для полей внутри списков.

export const encodeCursor = (id: number) => Buffer.from(`review:${id}`).toString('base64url');

export function decodeCursor(cursor: string): number {
  const [prefix, raw] = Buffer.from(cursor, 'base64url').toString().split(':');
  const id = Number(raw);
  if (prefix !== 'review' || !Number.isInteger(id)) throw gqlError('BAD_USER_INPUT', 'Некорректный курсор');
  return id;
}

async pageForMovie(movieId: number, first: number, after?: string | null) {
  const take = Math.min(Math.max(first, 1), 50);
  const beforeId = after ? decodeCursor(after) : undefined;
  const rows = await this.prisma.review.findMany({
    where: { movieId, ...(beforeId ? { id: { lt: beforeId } } : {}) },
    orderBy: { id: 'desc' },          // новые сверху; id монотонен → стабильный порядок
    take: take + 1,                   // +1: узнать, есть ли следующая страница, без COUNT
  });
  const page = rows.slice(0, take);
  const edges = page.map((r) => ({ cursor: encodeCursor(r.id), node: r }));
  return {
    edges,
    pageInfo: { hasNextPage: rows.length > take, endCursor: edges.at(-1)?.cursor ?? null },
  };
}

🔬 Под капотом: зачем edges, если можно просто список

edges кажутся лишней вложенностью. Но у ребра есть свои данные: курсор каждого элемента (можно продолжить с середины) и, в общем случае, атрибуты связи, а не узла (например, «когда пользователь добавил фильм в список» — это свойство ребра «пользователь → фильм», а не фильма). Формат делает пагинацию единообразной для любых списков API.

totalCount — дорогая штука на больших таблицах (COUNT(*) в PostgreSQL сканирует). Мы получили его бесплатно из загрузчика статистики, но в общем случае его делают отдельным полем, которое клиент запрашивает, только если нужен счётчик.

Курсор base64("review:123") легко раскодировать — «непрозрачность» тут договорённость, а не шифрование. Если важно, чтобы клиент не подделывал курсоры (например, курсор содержит позицию в сложной сортировке), его подписывают HMAC'ом. Для сортировки не по уникальному полю курсор должен содержать пару (значение, id) — иначе записи с одинаковым значением потеряются на границе страниц.

🔬 Под капотом: что происходит на проводе и почему clearAll()

Откройте DevTools → Network → WS в браузере с GraphiQL. Вы увидите: {"type":"connection_init","payload":{...}} → {"type":"connection_ack"} → {"type":"subscribe","id":"1","payload":{"query":"subscription Live ..."}} → на каждое событие {"type":"next","id":"1","payload":{"data":{...}}}. Периодически — ping/pong для обнаружения мёртвых соединений. По одному WebSocket можно мультиплексировать много подписок — у каждой свой id.

Функция context() для подписки вызывается один раз — при subscribe, а не на каждое событие. Значит, загрузчики из этого контекста живут столько же, сколько подписка — минуты и часы. Без clearAll() второй event показал бы averageRating, закэшированный при первом: нарушение правила «один запрос — один кэш» из раздела 5. Подписка — единственное место, где «запрос» длится долго, и кэш приходится сбрасывать вручную.

Токен передаётся не заголовком (у WebSocket в браузере нет API для произвольных заголовков), а в connectionParams сообщения connection_init. Проверяется он один раз при соединении: если токен истечёт через час, подписка продолжит работать. Это задание Production Hell №9.

🔬 Под капотом: чем это отличается от RabbitMQ и что будет при падении Redis

Redis Pub/Sub — «fire and forget»: сообщение доставляется тем, кто подписан прямо сейчас, и нигде не хранится. Инстанс перезапускался 2 секунды — события за эти 2 секунды его подписчики не получат никогда. Для живой ленты это нормально (клиент после переподключения перезапросит ленту обычным query), для денег и заказов — нет: там нужен брокер с очередями и подтверждениями или Redis Streams. Правило: подписка GraphQL — уведомление «что-то изменилось», а не единственный канал доставки данных.

Почему дата «сломалась»: in-memory PubSub передаёт объект по ссылке, createdAt остаётся Date. Redis передаёт строку JSON, и Date превращается в ISO-строку. Скаляр DateTime может принять строку, а может и нет — зависит от реализации; явное восстановление убирает зависимость от этого. Общий урок: всё, что уходит в шину, должно быть сериализуемым, и тип после десериализации может отличаться от исходного.

Это сделал app.enableCors() из шага 2.1 (разрешает любые origin — для лабы; в проде — явный список). Тот же preflight — причина, почему Apollo CSRF-защита из шага 2.4 пропускает запрос.

WebSocket под CORS не подпадает — браузер шлёт заголовок Origin, но проверять его должен сам сервер. Для публичных API с подписками это отдельная задача безопасности (Cross-Site WebSocket Hijacking при авторизации куками). У нас токен в connectionParams, а не в куках, — эта атака не работает.

// src/graphql/depth-limit.rule.ts — своё правило валидации (работает с AST, до выполнения)
import {
  FragmentDefinitionNode, GraphQLError, Kind, SelectionSetNode, ValidationContext, ASTVisitor,
} from 'graphql';

export function depthLimit(maxDepth: number) {
  return (context: ValidationContext): ASTVisitor => {
    const fragments = new Map<string, FragmentDefinitionNode>();
    for (const def of context.getDocument().definitions) {
      if (def.kind === Kind.FRAGMENT_DEFINITION) fragments.set(def.name.value, def);
    }

    const measure = (set: SelectionSetNode | undefined, depth: number, seen: Set<string>): number => {
      if (!set) return depth;
      let deepest = depth;
      for (const sel of set.selections) {
        if (sel.kind === Kind.FIELD) {
          if (sel.name.value.startsWith('__')) continue;                 // интроспекция не считается
          deepest = Math.max(deepest, measure(sel.selectionSet, depth + 1, seen));
        } else if (sel.kind === Kind.INLINE_FRAGMENT) {
          deepest = Math.max(deepest, measure(sel.selectionSet, depth, seen));   // фрагмент не добавляет уровня
        } else {                                                          // FRAGMENT_SPREAD
          const name = sel.name.value;
          if (seen.has(name)) continue;                                   // защита от циклов фрагментов
          deepest = Math.max(deepest, measure(fragments.get(name)?.selectionSet, depth, new Set(seen).add(name)));
        }
      }
      return deepest;
    };

    return {
      OperationDefinition(node) {
        const depth = measure(node.selectionSet, 0, new Set());
        if (depth > maxDepth) {
          context.reportError(new GraphQLError(`Глубина запроса ${depth} превышает лимит ${maxDepth}`,
            { nodes: [node], extensions: { code: 'QUERY_TOO_DEEP', depth, maxDepth } }));
        }
      },
    };
  };
}

import { Logger } from '@nestjs/common';
import { GraphQLSchemaHost } from '@nestjs/graphql';
import { Plugin } from '@nestjs/apollo';
import type { ApolloServerPlugin, BaseContext, GraphQLRequestListener } from '@apollo/server';
import { GraphQLError } from 'graphql';
import { fieldExtensionsEstimator, getComplexity, simpleEstimator } from 'graphql-query-complexity';

@Plugin()
export class ComplexityPlugin implements ApolloServerPlugin {
  private readonly logger = new Logger('Complexity');

  constructor(private readonly schemaHost: GraphQLSchemaHost) {}

  async requestDidStart(): Promise<GraphQLRequestListener<BaseContext>> {
    const { schema } = this.schemaHost;
    const max = Number(process.env.GQL_MAX_COMPLEXITY ?? 300);
    const logger = this.logger;
    return {
      async didResolveOperation({ request, document }) {
        const complexity = getComplexity({
          schema,
          query: document,
          operationName: request.operationName,
          variables: request.variables,
          // сначала — стоимость из опций полей (complexity: ...), иначе 1 за поле
          estimators: [fieldExtensionsEstimator(), simpleEstimator({ defaultComplexity: 1 })],
        });
        logger.log(`${request.operationName ?? 'anonymous'}: ${complexity}`);
        if (complexity > max) {
          throw new GraphQLError(`Слишком сложный запрос: ${complexity} (максимум ${max})`, {
            extensions: { code: 'QUERY_TOO_COMPLEX', complexity, max, http: { status: 400 } },
          });
        }
      },
    };
  }
}

🔬 Под капотом: validation rule против плагина и куда пропал наш код ошибки

Правило глубины — это обычное правило валидации graphql-js, как встроенные «поле существует» или «переменная объявлена». Оно получает AST и схему, обходит дерево visitor'ом и сообщает ошибки через context.reportError. Apollo кэширует результат валидации по тексту документа, поэтому одинаковые запросы проверяются один раз.

Посмотрите на ответ: extensions.code там GRAPHQL_VALIDATION_FAILED, а не наш QUERY_TOO_DEEP — Apollo перезаписывает код всем ошибкам валидации, но остальные поля extensions (depth, maxDepth) сохраняет. Урок: не полагайтесь, что код переживёт все слои, — кладите детали в отдельные поля.

Сложность считается в плагине на хуке didResolveOperation, потому что ей нужны значения переменных (limit: $n) — а на этапе валидации они ещё не подставлены. Поле http в extensions — служебное: Apollo по нему выставляет HTTP-статус 400 и не отдаёт его клиенту. Важная дыра: плагины Apollo работают для HTTP, а подписки идут через отдельный WebSocket-сервер — проверьте сами, защищены ли они (Production Hell №3).

11. Глоссарий терминов #

В порядке первого появления в тексте.

1. Схема (schema) ↩ — полное описание API в системе типов GraphQL: все типы, поля, аргументы и корневые типы Query/Mutation/Subscription. Публичный контракт между сервером и клиентами.

2. Резолвер (resolver) ↩ — функция, вычисляющая значение одного поля одного типа. Получает (parent, args, context, info), может вернуть значение или промис.

3. Проблема N+1 ↩ — ситуация, когда для списка из N элементов выполняется 1 запрос за списком и ещё N запросов — по одному на каждый элемент — за связанными данными. В GraphQL возникает естественно, потому что резолвер поля вызывается для каждого родителя отдельно.

4. DataLoader ↩ — библиотека, собирающая вызовы load(key) за один тик event loop в один батч и кэширующая результаты в рамках одного запроса. Стандартное средство против N+1.

5. extensions ↩ — произвольный объект в ошибке GraphQL (и в ответе целиком) для машинно-читаемых данных. По соглашению extensions.code — код ошибки.

6. SDL (Schema Definition Language) ↩ — текстовый язык описания схемы: type Movie { title: String! }. Не зависит от языка программирования.

7. Code-first ↩ — подход, при котором схема генерируется из кода (классов с декораторами). Противоположность — schema-first, где источником истины является SDL.

8. Подписка (subscription) ↩ — операция GraphQL, открывающая поток событий: сервер выполняет selection set на каждое событие и пушит результат клиенту, обычно по WebSocket.

9. @deprecated ↩ — встроенная директива схемы, помечающая поле или значение enum как устаревшее (с причиной). Поле продолжает работать, но инструменты предупреждают клиентов.

10. Операция (operation) ↩ — исполняемая единица документа: query, mutation или subscription. Может иметь имя и объявления переменных.

11. Selection set ↩ — набор полей в фигурных скобках, которые клиент хочет получить у объекта. Определяет форму ответа.

12. Переменные (variables) ↩ — значения аргументов, передаваемые отдельно от текста запроса ($id). Позволяют не менять текст запроса и защищают от инъекций.

13. Алиас (alias) ↩ — переименование поля в ответе: latest: reviews(first: 3). Позволяет запросить одно поле несколько раз с разными аргументами.

14. Фрагмент (fragment) ↩ — переиспользуемый кусок selection set, привязанный к типу (fragment X on Person). Инлайн-фрагмент ... on Movie выбирает поля конкретного типа в полиморфном поле.

15. Директива (directive) ↩ — аннотация с @, меняющая выполнение или описание: @include, @skip в запросах, @deprecated в схеме.

16. Скаляр (scalar) ↩ — листовой тип без полей: Int, Float, String, Boolean, ID и пользовательские (DateTime). Определяет сериализацию и разбор значения.

17. Input type ↩ — тип-объект для аргументов. Его поля не имеют аргументов и резолверов и не могут ссылаться на object-типы.

18. Интерфейс (interface) ↩ — абстрактный тип с набором общих полей, которые реализуют несколько object-типов. Общие поля запрашиваются без фрагментов.

19. Юнион (union) ↩ — абстрактный тип «одно из перечисленных» без общих полей; конкретные поля выбираются только через инлайн-фрагменты.

20. Non-Null (!) ↩ — модификатор типа, гарантирующий, что значение никогда не будет null. По умолчанию в спецификации все типы nullable.

21. Корневые типы (root types) ↩ — типы Query, Mutation и Subscription — точки входа в граф. Их поля — это «эндпоинты» API.

22. Мутация (mutation) ↩ — операция изменения данных. Поля верхнего уровня выполняются строго последовательно.

23. AST (Abstract Syntax Tree) ↩ — разобранный в дерево объектов текст запроса. С ним работают валидация, анализ сложности и исполнитель.

24. Контекст (context) ↩ — объект, общий для всех резолверов одного запроса. Создаётся функцией context() на каждый запрос; в лабе содержит пользователя и загрузчики.

25. Резолвер по умолчанию ↩ — встроенный резолвер, возвращающий parent[fieldName]. Поэтому для простых полей резолвер писать не нужно.

26. Field resolver (@ResolveField) ↩ — явный резолвер поля объектного типа в NestJS; получает родительский объект через @Parent(). Используется для связей и вычисляемых полей.

27. Всплытие null (null propagation) ↩ — правило: если non-null поле получило null (из-за ошибки), null передаётся ближайшему nullable-родителю; при отсутствии таких — data становится null.

28. Интроспекция ↩ — способность схемы описывать саму себя через поля __schema и __type. На ней работают IDE, генераторы кода и документация.

29. __typename ↩ — мета-поле любого объектного типа, возвращающее имя конкретного типа. Нужно для юнионов/интерфейсов и ключей клиентских кэшей.

30. graphql-ws ↩ — протокол (и библиотека) GraphQL поверх WebSocket, подпротокол graphql-transport-ws: connection_init, subscribe, next, complete, ping/pong. Заменил устаревший subscriptions-transport-ws.

31. Ошибки как данные (errors as data) ↩ — подход, при котором ожидаемые исходы операции моделируются типами схемы (юнион результата), а не записями в errors. Делает ошибки типизированными и видимыми в интроспекции.

32. Connection (Relay) ↩ — стандартный формат курсорной пагинации: edges { cursor node } + pageInfo { hasNextPage endCursor }.

33. Курсор (cursor) ↩ — непрозрачная строка, указывающая позицию в списке. Клиент передаёт её в after, не разбирая содержимое.

34. Сложность запроса (query complexity) ↩ — оценка «стоимости» запроса до выполнения: сумма стоимостей полей с множителями для списков. Запросы дороже лимита отклоняются.

35. Persisted queries ↩ — механизм, при котором клиент отправляет не текст запроса, а его хеш, а сервер выполняет только заранее известные запросы. Защищает от произвольных запросов и улучшает кэширование.
